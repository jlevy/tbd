The shortcut is long and heavily weighted toward proxied-cloud diagnosis. What it lacks is a
plain, ordered, reproducible fresh-machine procedure that an agent on a brand-new Linux box can
execute top to bottom and then verify.

CHANGES
1. Fix the corner-case table: item 2 claims 'gh exists but wrong version -> reinstall via ensure
   script', which the script does not currently do. After the version-floor bead lands, this
   becomes true; the doc and script must be made consistent in the same PR.
2. Add a numbered fresh-machine setup section covering: run the ensure script, confirm the
   version floor, authenticate, install the pinned gh-stack extension, install the pinned
   official skill.
3. Add an explicit verification checklist with expected output for each command, so validation
   is pass/fail rather than a judgment call:
     gh --version              -> >= 2.97.0
     gh auth status            -> Logged in to github.com
     gh extension list         -> github/gh-stack v0.1.0
     gh skill list             -> gh-stack present
     gh stack --help           -> exits 0
4. Document the keyring-vs-GH_TOKEN distinction. The script's else-branch prints
   'NOTE: GH_TOKEN not set - some operations may require authentication' even when gh is fully
   authenticated via keyring, which is exactly what this session's SessionStart hook printed on a
   working machine. Either soften that message to check real auth first, or explain it.
5. Keep the proxied-session material, but move it below the common path so the fresh-machine
   procedure is what a reader hits first.
