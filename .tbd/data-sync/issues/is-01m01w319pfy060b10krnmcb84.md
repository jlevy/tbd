`mappings/ids.yml` is keyed short -> ulid and merged with `merge=union`. That direction is the whole source of the bug class fixed in tbd-ysz0 / PR #232: two clones can independently mint the same short ID for different beads, union merge keeps both lines, and the loader must then arbitrate.

Inverting the file to `<ulid>: <shortid>` makes union merge collision-proof by construction. ULIDs are globally unique, so a union merge can only ever produce the same key twice with the same value — harmless and idempotent. No bead is ever unrenderable, and the entire tiebreak / derivation / convergence apparatus in PR #232 becomes unnecessary.

This is the structural fix; #232 is the repair. Worth doing because it deletes the problem class rather than compensating for it.

Cost: on-disk format change plus a migration, so it needs a format version bump. Note that `serializeIdMapping` sorts by short ID for stable diffs; a ULID-keyed file sorts by ULID instead, which is creation order — arguably better for diffs.

Related: the same reasoning drives the storage decision for agent identity records (research-2026-08-14-agent-and-session-identity.md section 5.3/5.4), which chose one-file-per-canonical-ID for exactly this property.

Raised as S1 in the senior review of PR #232.
